## 2. 当前路线与设计变更

取件助手继续使用 Flutter + Riverpod + GoRouter + sqflite，Android 为主。

取件码主线为本地规则解析：主动粘贴／手动录入 → 通知候选 → 可选短信，再补地址分组、规则管理、备注分享、大字和标准桌面小组件。ExpressAssistant的登录配置参考在M0落地，统一刷新协调、分来源报告及分批提交提前到M1，真实平台取件获取仍在M5，不作为本地版本交付前提。

直接借鉴 Parcel 的规则和交互，源码参考提交为 `d7e4c974ffd1e4de2da9291df0d295856cd89818`，对应文件链接及采用／不采用范围见设计第2节。已核实 Parcel 的身份码入口使用官方 App 深链，并非应用内生成身份码。本次没有复制 Parcel 代码；未来移植时保留其 MIT 版权与许可，并记录来源。

新增ExpressAssistant固定参考提交 `5adcfa780017ab0fb9888e5aaeef7b6a8d311209`，已读取登录、同步、平台订单／SSR、取件文本解析与存储源码及MIT许可，未安装或实际请求用户账号。取其登录初始化、互斥同步、渠道状态和字段保留机制；不复制全局清Cookie、普通偏好存凭证、只按运单号去重、异常返回空列表、固定渠道覆盖优先级或业务功能全集。

架构调整为“TextEvidence → 解析”和“StructuredPickupCandidate → 校验”两路汇入同一PickupImportService，再事务合并；SyncCoordinator负责single-flight、scope报告、超时取消与迟到批次拦截。平台侧签收不等于用户已取；合法空、失败、部分成功与需登录必须分别显示，不能都提示“已刷新”。

M5比较A（WebView内DOM／已有结构化数据）、B（Cookie签名HTTP／SSR研究）和C（官方App／文本导入回退）。默认采用通过实测的A，B仍关闭；真要采用B，先补会话安全存储、撤销、客户端与测试的独立设计。首版只验证一个平台账号，不因有scope字段就承诺多账号。来源固定链接、路径出口见设计2.3、3.3及6.3节。

关键约定：不强制登录；来源与平台分离，未知平台不能当淘宝；分组标签不参与记录身份；已取件只由用户确认；重复采集不能清空已取时间和人工字段。

方案规划后已明确只推送GitHub，并同步过README。此次双参考重设计仅改需求、设计、交接三份docs，不改README、应用代码、依赖或资产配置；未复制参考项目代码。以后实际移植时分别记录两个项目的固定提交、原文件、版权与许可。

## 4. 现有代码地图与测试注意点

```text
lib/main.dart                         打开DB，构建仓库并注入ProviderScope
lib/app/                              app、theme、buildAppRouter路由工厂
lib/core/config/platform_config.dart  assets平台配置读取
lib/core/webview/                     登录提示检测
lib/features/pickup/domain/           模型、平台枚举、仓库接口
lib/features/pickup/data/             SQLite仓库、H5同步服务
lib/features/pickup/presentation/     列表、详情、录入及Riverpod控制器
lib/features/auth/                    登录态仓库和身份码WebView
lib/features/settings/                配置展示、退出、清空已取
```

- repositoryProvider 保留抽象接口；widget 测试使用 `test/helpers/memory_pickup_code_repository.dart`，避免 FakeAsync 与 sqlite_ffi 原生事件端口挂起。
- 仓库／迁移测试用真实 SQLite FFI，不能用 widget 内存实现代替；两种仓库合并语义须一致。
- buildAppRouter 保留工厂，不恢复全局单例路由，避免测试间导航状态泄漏。
- 平台枚举为 PickupPlatform，避免与 dart:io Platform 同名。
- Cookie API 为 `WebViewCookieManager().clearCookies()`；登录态留在系统 WebView 沙箱，不复制 Cookie 到普通存储。
- URL 与选择器以 `assets/platform_config.json` 为准；阶段0文档只是历史来源，不将示例 URL 当成有效地址。

## 6. 执行顺序与阶段出口

| 阶段 | 开发起点与出口 |
| --- | --- |
| M0 | 先确认SDK路径；M0-B参考ExpressAssistant登录初始化，保留Cookie沙箱；按A/B/C/D修复验证 |

| M2 | Kotlin持久队列 → 通知提取／白名单 → 接入M1协调器、提交后ack → 权限与进程恢复矩阵 |
| M3 | 可选短信、规则试解析、地址分组、备注分享、官方App身份码入口 |
| M4 | 标准小组件、快照、大字／暗色；独立验证后台Flutter入口，失败保留前台恢复处理 |
| M5 | M5-A适配H5契约 → M5-B真机DOM字段 → M5-C比较获取路径 → M5-D集成通过来源；任务编号与A/B/C获取路径分别识别，不默认实施Cookie外导 |

完整任务包及每包验收见设计第8节。每个实现提交最多3文件（含测试），较大的任务包先拆契约、实现、接线和验收。每次完成后更新本交接文档的真实状态，不一次实现整条链路。

首个可用版本出口为 M0—M2：无需登录或短信权限也可用本地功能；通知已送达的候选先可靠暂存，恢复App后处理。不承诺 M2 已经支持 App 关闭时自动解析和实时更新小组件。

M1-G/H必须使用fake覆盖合法空结果、失败保留旧数据、部分批次提交、同时刷新附着、超时取消、来源过期和迟到结果；不等待真实平台数据才搭底座。M5-C研究可在M1底座完成后先做脱敏fixture，不以研究完成替代平台上线或真机账号验证。

后续数据升级必须保留旧ID／已取状态／取件时间；不能通过删除数据库解决迁移失败。主库只由Dart管理，Kotlin只写候选队列，避免双端维护业务表。
